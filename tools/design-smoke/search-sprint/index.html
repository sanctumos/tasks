Search at every level — proposed integrations

Ranked by necessity. Each comp shows the level, the search behavior (live / submit / client-side), and what it covers. Prototype only — no prod edits.

R1 Global nav omnibox — search everything from anywhere Live dropdown Enter → results page

The single biggest gap: there is no way to search across tasks, docs, people, and boards from the chrome. A navbar omnibox (keyboard shortcut / or Ctrl K) with a live dropdown of top hits grouped by entity, and Enter falling through to a full results page. Backed by a new GET /api/search.php?q= that fans out to tasks (title/body), documents (title/body), users (username), and projects (name) with per-entity LIMIT 5. Non-stateful: the dropdown is ephemeral; the results page carries ?q= in the URL so it's shareable.

R2 Home filter bar — upgrade to live update Live (debounced) URL-stateful

Home already has a submit-based filter bar, but it forces a full page reload and hydrates the heavy cross-project board. Proposal: keep the same fields, make q + selects fire a debounced (300ms) fetch against list-tasks.php, swap only the results region, and reflect state in the URL (?q=&status=&mine=1) so a reload or share reproduces the view. This also fixes the "deep-link forces the heavy board on" wart — a live-filtered Home can serve results from the light path.

R3 Project → Tasks tab — board-local search + quick chips Client-side live Server for big boards

The project workspace is where people live, and today the only filter is "assigned to me." Proposal: a search box above the kanban that filters the cards already on the page client-side (instant, no round trip), plus one-tap chips for status and priority that combine with the text query. Boards over ~200 cards fall back to a server round trip (list-tasks.php?project_id=&q=) so we never ship a giant DOM to filter. Stateful in the tab URL (?tab=tasks&q=) so a refresh keeps the view.

R4 Docs hub + project Docs tab — title/body search Submit-based Server-side

Documents are the long-term memory and today you can only browse by project/folder — no q in the UI or the API. Proposal: a search box on the Docs hub (all projects you can reach) and on each project's Docs tab (scoped to that project), submit-based with results ranked title-match-first, then body snippet with highlight. Requires adding q to list-documents.php (SQL LIKE on title + body, same pattern as tasks). Stateful via ?q=; no live dropdown needed here — docs corpora are small and reads are deliberate.

R5 Task detail — find in thread Client-side Non-stateful

Long comment threads (design reviews, client back-and-forth) have no way to jump to a keyword. Proposal: a small "Find in thread" box on the task page that highlights matches in comments and hops between them — pure client-side, no server, no URL state. Attachments list gets the same filter box (matches file names). Low cost, real quality-of-life on big cards.

R6 Activity + Notifications — text filter Client-side live Non-stateful

Both feeds are browse-only today. Proposal: a filter box above the feed that narrows the loaded rows client-side (matches actor, task title, project name), plus type chips on Activity (comments / status changes / creates). Deliberately non-stateful and client-only: feeds are ephemeral scans, not reports — nobody bookmarks a filtered activity view. Server-side search of the full audit trail stays an admin/API concern.

R7 Users admin — live list filter Client-side live Non-stateful

The admin users table is a full dump. Proposal: a filter box that narrows rows client-side on username / role / status. Same pattern could serve the Members tab on projects and the user↔projects ACL page. Lowest rank — the user count is small and admins tolerate scrolling — but it's nearly free once the client-side filter helper exists for R3/R5/R6.
